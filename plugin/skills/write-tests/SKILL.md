# 写测试

测试是给以后的 agent 和用户看的"规则清单"：改代码时它能抓到规则被破坏。写空了等于没写；重复的、说不出守什么的不写。

## 什么时候写

需求在分支上常常还在试：做出来看一眼，再改。边做边写的测试会跟着一遍遍重写。所以新测试留到要合并时才写。

- **分支上开发时不写新测试，已有的测试也不改。** 每做完一轮跑一次 `testpace focused`（它跑的是已有的测试），只看结果、不追着修到全过：因为用户这次改了需求才不过的，留着，不改测试；和这次需求无关的（这次的改动弄坏了别的功能），当场改这次自己写的代码；查出来是原来的业务代码就有问题的，照"写完"第 1 条先停下来告诉用户。做完一个任务时不要自己开始写测试：告诉用户做完了、测试还没写，用户说合的时候再写。
- **用户说要合并这个分支时才写**（"合""可以合了""提 PR"）。写新测试，把因为需求变了而不过的旧测试照定下来的规则改掉（用户自己提出的改动不用再问），跑通、提交，再照 gatelight:merge 技能合。这次没改到规则的（小改动、只是换写法）不用写，直接合。
- **交给一个子代理写**（有起子代理的工具时；没有就自己写）。写代码的和写测试的分开，不顺着写代码时的思路去写。交代给它的话里要有三样：
  - **这次定下来的规则，用白话一条条列出来。** 照和用户定下来的写，不是照代码现在的做法写。子代理没看过这次对话：只看代码写出来的测试是"代码怎么做就怎么期望"，代码里的错也被当成对的。
  - **这次改了哪些文件**（`git diff --stat <默认分支>...`），和开发中留着没过的旧测试是哪几个。让它照本技能写新的、改旧的，写完用 `testpace files` 跑通。
  - **测试没过、它认为是业务代码不对的，不改业务代码**：回来说明是哪条规则、实际结果是什么。

  子代理回来后跑 `testpace focused`，通过了提交。它说业务代码不对的，照"写完"第 1 条办：先停下来告诉用户。
- **一个例外，开发中当场做**：修已定规则（已经合进默认分支的）的 bug，先写能重现它的测试，确认它失败，再修。

## 先分档

- **小改动**：文字、样式、注释、显示用的配置。不写测试；命中清单（见下面）的照样要查。
- **改到规则**：先看它属于下面哪一类，再决定写不写、写在哪一层。

## 哪些写，哪些不写

人验收时看不到那么细，也不可能每次把所有页面再看一遍。所以值得守的不只是"出了错代价大"的地方，也包括"人容易漏看、容易忘"的地方。写下来的测试分两层：

**必跑层**（出了错代价大，在页面上又看不出来）：

- **钱**：金额怎么算、能不能超、退不退。
- **权限**：谁能看、谁能做。
- **状态与数据**：什么状态下能做、不能做；数据会不会丢、会不会错。会让数据出错的校验（重名、证件号）算这一类。
- **每个功能的主流程页面测试**：从头走通一遍（比如"下单后订单出现在列表里"），查前后端接不接得上、页面打不打得开。走完整流程的测试最难糊弄。

钱、权限、状态与数据写在接口层（直接调接口、连真库），测透，边界都要有。

**细节层**（人单次能看到，但功能多了会漏、会忘）：

- 界面细节：按钮什么时候灰、弹窗和抽屉怎么开关、草稿留不留。
- 样式和摆放里用户在意的那些。
- 提示文字、默认值、名单怎么分组、必填项。

**另外**：修过的 bug 留一条能重现它的测试，放在能重现它的最低一层。

**不写**：

- 在页面上重复验证接口层已经守着的规则。只有前端自己才有的规则（比如前端自己算的数）才在页面层测。
- 测框架或数据库本身、原样转交的代码、配置常量、不可能发生的情况、凑覆盖率的测试。

**什么时候跑**不归这里管，是 testpace 的事：分支上只跑这次改到的测试和最相关的几个，合回默认分支时两层全部跑一遍。所以不要为了省时间少写该写的测试，也不用为了快把测试挪来挪去。

**怎么写**：

- 测试名用白话写它守的规则（"余额不够时不能下单"），说不出守什么的不写。接口层一个测试守一条规则；页面测试每个都要先准备一遍数据，可以顺着一条流程查几处，不强求拆开。
- 测结果，不测内部做法。一条规则只在一处测透。
- 断言要检查结果对不对（具体的值、具体的报错），不能只检查"有返回值""没报错"。

## 放在哪一层测

- 三层从低到高：纯函数 → 接口（连真库）→ 页面。一条规则放在能抓到它的最低一层，下面一层抓得到的，不放到上面一层测。页面测试最贵（要起浏览器、走整条链路），只给主流程和界面细节用。
- 截图对比默认不做，只给项目说明里点名的少数关键页面做。
- 依赖用真的：数据库用 napbox 起的真实实例。替身只用在两处：外部第三方服务的边界（支付、短信这类），和只有浏览器端才有的状态（时间、定位、断网、浏览器权限）。环境照 napbox 技能搭，和线上同结构。

## 性质测试：一句"不可能错"的话，让工具找反例

举例子的测试只测到你想到的情况；agent 写的代码常在没想到的边界上出错。钱、权限、数据的规则里，能说成一句"总是成立"的话的，在举例子之外再加一条性质测试：写下这句话，让工具生成成百上千组输入去推翻它。

- **适合写成性质的**：
  - 不变量：实付不会是负数，也不会比原价多；各项金额加起来等于合计；没有权限的人对任何一条记录都读不到。
  - 编码再解码得回原值：序列化、解析、导入导出。
  - 做两次和做一次一样：迁移、重试、去重、规范化。
  - 两种算法结果一样：优化过的写法和简单直白的写法（见下面"大改"）。
- **用项目已有的库**：JS/TS 用 fast-check，Python 用 Hypothesis，Rust 用 proptest，Java 用 jqwik。项目里还没有，用白话问用户一句"要装一个测试用的库，可以吗"，库由你挑，不让用户选；同意了只加成测试用的依赖（devDependency 这类）。
- **性质里用断言，不要返回 true/false**：返回 false 的性质失败时只说"不成立"，看不出是哪个值不对。
- **失败时要打印出断言**：fast-check 默认把断言藏在错误的 cause 里，有的运行器不打印它。每次 `fc.assert(性质, { includeErrorInReport: true })` 都带上这个设置；要统一写在共用设置里，写成 `fc.configureGlobal({ ...fc.readConfigureGlobal(), includeErrorInReport: true })`，直接传新对象会冲掉已有的全局设置（`numRuns`、`seed`）。
- **边界值照样写成具体例子**：输入是随机的，0、刚好等于门槛这类边界不一定每次都碰得到。性质补在例子之外，不替代例子。
- **找到的反例写成例子**：性质测试失败时会打印最小的反例和随机种子，用这个种子能复现；修 bug 时把这个反例写成一条具体的测试，先确认它失败再修。
- **放在能抓到它的最低一层**（多数是纯函数）：每组输入都跑一遍。连真库的接口测试把次数调小（比如 `numRuns: 20`），每组输入从干净的数据开始；页面测试不写性质。

## 已定和还在试

- **已定**：合进默认分支就算已定，合之前把测试写上（见"什么时候写"）。
- **还在试**：分支上还没合的都算。不写测试，自己临时跑通就行。
- **合并时用户说"这块还在试、先合进去"**：那一块先不写测试，合进去以后也还算在试。它之后修过的 bug 记进 `.testcraft/rules/<编号>.md`（一条一个文件，标题写规则，正文写修过的 bug）；用户说定了的时候写测试，把记过的 bug 补成测试，然后删掉那条记录。
- 修已定规则的 bug：先写能重现它的测试，确认它失败，再修。
- 要改已定的规则（已定的规则以测试名为准；包括为此删测试、让测试不跑、改期望值）：先用白话问用户一次，用户同意了再改。用户这次自己提出要改的不用再问。不用另外写记录。
- 测试上别的调整（跟着代码改接法、换写法、挪位置、删重复的）自己定，不问用户，也不用写说明。
- 整块功能不要了：规则和测试一起删。

## 清单：写不成测试的坑

`.testcraft/checklist/<编号>.md`（清单目录下一层的每个 `.md` 都是一条）记写不成测试、又能从改动看出来的坑（老数据缺新字段还能不能读、改了接口要同步改哪几处、上线配置要跟着改），一条一个文件。改动命中某条的触发条件时，按它的"怎么查"查一遍，查出这次改动带来的问题就改好。只是提醒：不用写下怎么查的。`testcraft checklist` 列出这次命中的条目和各条怎么查；落地前的整组里也会说一遍。

- **什么时候加一条**：修 bug、出事故后，这个坑能写成测试的写测试，不进清单；写不成测试（跨模块的约定、老数据兼容、部署和配置），又能从改动的文件或增删的行看出来的，加一条。gatelight 另带几条很多项目都会碰到的默认条目（比如开发登录只在开发环境有），接入时放进来；已接入的项目补新的默认条目照 `gatelight:setup-testcraft`。
- **怎么写**：

  ```markdown
  # 会话记录加字段时，老记录也要读得出来

  ## 触发

  - `src/session/**` 改到 `interface \w+Message`
  - `src/storage/schema.ts`

  ## 怎么查

  新字段在读老记录时有默认值；拿一份改动前的会话记录恢复一次，能打开。

  ## 来由

  fix/resume-crash：加了字段后，恢复老会话直接崩溃。
  ```

  触发每行一条：行首反引号写路径规则（几个用、隔开），后面可以加"改到"和反引号括起的文字（正则），这些文件增删的行里有这段文字才算。触发写得窄一点，命中了就该真去查；什么都触发的条目没人会认真查。
- 按分叉点那一版的清单提醒：这次新加的条目合并后才生效，这次删了、改了的照旧按原来的提醒。
- 条目不再有用（坑已经被测试守住、代码没了）才删。删、改条目自己定，不问用户。

## 大改

新旧两套代码先并行，确认结果一样再换掉旧的。不删测试、不做假实现来让测试变绿。

- **用差分测试确认结果一样**：同样的输入同时喂给旧代码和新代码，结果要一样。旧代码原样留一份（旧函数或旧文件）让测试调得到。输入用性质测试的库随机生成，或者取一批真实数据的样本；真实数据先脱敏，不放进版本库。和结果无关的差别（空格、字段顺序、时间戳）先统一掉再比；新代码有意改了的地方，在测试里逐条列出来，不要放宽整个比较。
- **换掉旧代码时**：先确认每条规则都有普通的测试（例子或性质）守着，再删旧代码和差分测试。

## 测试时好时坏

同一份代码，一个测试这次没过、再跑又过了（整组里没过、单独跑能过，也算），就是时好时坏。testpace 在测试结果里点名、记进名单的（`testpace status` 列出名单和日志；项目的 `files` 经 `testpace run` 跑才有名单），就是这种。它说明测试或代码里有个条件没管住。靠重跑过关，以后它再红大家都当它又抽风了，真坏的时候也没人信它。

- **不靠重跑过关**：当一个要修的问题。测试或它测的代码这次改过的，当场照下面找原因（原因在业务代码里的照样先停下来）；和手上的活无关的，告诉用户是哪个测试、哪次跑没过、日志在哪（`testpace status` 的名单里有），问要不要现在修。
- **这些不算修，不要做**：加固定等待（`sleep`、`setTimeout`、`waitForTimeout`、等几秒再继续）；加重试或调大重试次数（测试里自己写的循环重试，测试文件里设的重试如 `test.describe.configure({ retries })`、`jest.retryTimes()`，配置里的 `retries`）；放大超时；跳过，或标成"已知不稳定"；把断言放宽到几种结果都算对。它们只是把问题藏起来。等一个具体的条件（元素出现、请求返回、数据写进库，`expect.poll`、`toPass`、`waitFor` 这类按条件轮询）是对的写法；只把这个等待的超时调大，不算修。
- **先找原因**，常见的几种：
  - 测试之间共用数据：两个测试改同一条记录、同一个账号，一起跑时互相踩。每个测试自己建数据，名字带唯一后缀。
  - 时间、随机数没固定：跨零点、跨月、时区、按当前时间算的到期；随机生成的输入。被测代码能从参数拿到当前时间、随机种子的，测试传固定值；页面测试里浏览器端的时间可以用替身固定（"放在哪一层测"）；测试不依赖那个时间、随机值就能修的（比如比较前先排序、名字加唯一后缀），在测试里修；非依赖不可、后端代码又只能自己读系统时间、自己生成随机数的，是业务代码的写法让它测不稳，先告诉用户。
  - 没等到真正准备好：页面还在加载、请求还没回来、后台任务还没跑完就去检查。等那个具体的条件，不等固定时长。
  - 依赖先后顺序：单独跑能过、跟着别的测试跑才没过（或者反过来），说明前一个测试留下了东西，或者这个测试靠前一个准备的东西。
  - 依赖外部服务：网络、第三方接口。照"放在哪一层测"，外部第三方服务用替身。
  - 业务代码在并发下本身有问题：几个请求同时到、几套环境一起跑时才出错。
- **先让它稳定地没过**：照怀疑的原因造出条件（把时间固定到跨零点、把两个测试放一起跑、换个顺序、同时发几个请求），让它每次都没过，才算找到了原因（`testpace files --repeat N <文件:行号>` 连跑 N 次、没过就停，可以拿来造失败；共用数据、先后顺序这类单独跑能过的，把造出失败时一起跑的几个文件都给它）；改完在同样的条件下跑通。造不出来，说明还没找到原因，不要凭猜测改。
- **原因在业务代码里**：这是测试抓到的真问题，先停下来用白话告诉用户，不要自己改业务代码，也不要改测试去迁就它。
- **实在找不到原因**：删掉，比留一个时好时坏的测试好；不要改成跳过。怀疑是业务代码在并发下的问题、又造不出来的，先告诉用户，不要删。删之前看这条规则还有没有别的测试守着，没有的完成时告诉用户一句这条规则暂时没有测试守着。删了的测试不会经连跑去掉名单：在认出它的工作区里把它原来的文件整个跑一次（`testpace files <文件>`），全部通过，testpace 就把它从名单上去掉。
- **修好的**：用 `testpace files --repeat 3` 在造出失败的同样条件下连跑 3 次（单独跑就会失败的给 `<文件:行号>`；一起跑才失败的，给一起跑的那几个文件），跑的过程中不改代码。输出里说了把它从时好时坏名单上去掉才算修好；只说"都通过"、没说去掉的（比如有一次是框架重试后才过），用 `testpace status` 看它还在不在名单上，在的就还没修好。

## 写完

1. `testpace focused`（或 `testpace files`）确认测试通过。测试没过的改测试或改这次自己写的代码，不要改业务代码去迁就测试；测试发现了业务代码里别的问题（不是用户这次让修的那个 bug），先停下来告诉用户。
2. `testcraft checklist`：命中的条目按"怎么查"查一遍。没改到规则的小改动也会命中，照样要查。
3. 不用证明测试管用，不用请别的 agent 复查，不用写改动记录。写测试的时候就按上面的约定写对：断言检查具体的结果，修 bug 的测试先看它在修之前失败。
4. 完成时只对用户说业务上的事：改了哪些已定的规则（都该是先问过的）、哪些规则还在试、哪些规则这次没有测试守着。测试怎么写的、跑了哪些命令不用说。
