# 写测试

测试是给以后的 agent 和用户看的"规则清单"：每个测试守一条规则，改代码时它能抓到规则被破坏。写多了拖慢整组、重构一次大片变红；写空了等于没写。

## 先分档

- **小改动**：文字、样式、注释、显示用的配置。不写测试，不留记录；命中清单（见下面）的照样要查、要记。
- **改到规则**：价格怎么算、谁能看什么、数据怎么存、业务流程怎么走。按下面做。

## 测什么、测多深

- 每个测试守一条规则，**测试名用白话写这条规则**（"余额不够时不能下单"），说不出守哪条规则的不写。
- 测多深看出错的损失：钱、权限、数据会不会丢，测透，边界都要有；一般功能测主要情况；界面摆放、文字基本不测，靠人看。
- 测结果，不测内部做法。一条规则只在一处测透，每个入口最多再留一条走通的检查。
- 不写：测框架或数据库本身、原样转交的代码、配置常量、不可能发生的情况、凑覆盖率的测试。
- 断言要检查结果对不对（具体的值、具体的报错），不能只检查"有返回值""没报错"。

## 放在哪一层测

- 一条规则放在能抓到它的最低一层测。三层从低到高：纯函数 → 接口（连真库）→ 页面。下面一层抓得到的，不放到上面一层测。
- 页面测试只给涉及界面和整条链路的规则，测用户能不能走通流程（比如"下单后订单出现在列表里"），不测摆放和文字。环境照 napbox 技能搭，和线上同结构。
- 截图对比默认不做，只给项目说明里点名的少数关键页面做。
- 依赖用真的：数据库用 napbox 起的真实实例。替身只用在两处：外部第三方服务的边界（支付、短信这类），和只有浏览器端才有的状态（时间、定位、断网、浏览器权限）。

## 性质测试：一句"不可能错"的话，让工具找反例

举例子的测试只测到你想到的情况；agent 写的代码常在没想到的边界上出错。钱、权限、数据的规则里，能说成一句"总是成立"的话的，在举例子之外再加一条性质测试：写下这句话，让工具生成成百上千组输入去推翻它。

- **适合写成性质的**：
  - 不变量：实付不会是负数，也不会比原价多；各项金额加起来等于合计；没有权限的人对任何一条记录都读不到。
  - 编码再解码得回原值：序列化、解析、导入导出。
  - 做两次和做一次一样：迁移、重试、去重、规范化。
  - 两种算法结果一样：优化过的写法和简单直白的写法（见下面"大改"）。
- **用项目已有的库**：JS/TS 用 fast-check，Python 用 Hypothesis，Rust 用 proptest，Java 用 jqwik。项目里还没有，用白话问用户一句"要装一个测试用的库，可以吗"，库由你挑，不让用户选；同意了只加成测试用的依赖（devDependency 这类），加依赖会被放水检查标出，在放水理由里写为什么加。
- **性质里用断言，不要返回 true/false**：`testcraft prove` 只认断言失败。返回 false 的性质失败时没有断言的样子，证明不了它能抓错。
- **失败时要打印出断言**：fast-check 默认把断言藏在错误的 cause 里；Node 22 及以下的 node:test 输出不到终端时不打印它，`testcraft prove` 就认不出是断言失败。每次 `fc.assert(性质, { includeErrorInReport: true })` 都带上这个设置，不影响别的设置；要统一写在共用设置里，写成 `fc.configureGlobal({ ...fc.readConfigureGlobal(), includeErrorInReport: true })`，直接传新对象会冲掉已有的全局设置（`numRuns`、`seed`）。vitest 会打印 cause，可以不加。别的运行器先故意让性质失败一次，看输出里有没有断言原文。
- **边界值照样写成具体例子**：输入是随机的，0、刚好等于门槛这类边界不一定每次都碰得到。性质补在例子之外，不替代例子。`testcraft prove` 证明不了时，补具体例子，不要反复重跑碰运气。
- **找到的反例写成例子**：性质测试失败时会打印最小的反例和随机种子，用这个种子能复现；修 bug 时把这个反例写成一条具体的测试，先确认它失败再修。
- **放在能抓到它的最低一层**（多数是纯函数）：每组输入都跑一遍。连真库的接口测试把次数调小（比如 `numRuns: 20`），每组输入从干净的数据开始；页面测试不写性质。

## 规则还没定时

- **暂定**（用户说"这块还在试"，或规则还在来回改）：不写正式测试，自己临时跑通就行；修过的 bug 记进 `.testcraft/rules/<编号>.md`（一条一个文件，标题写规则，正文写修过的 bug）。
- **已定**（默认合进默认分支就算已定）：写正式测试，把 `rules/` 里记过的 bug 补成测试，然后删掉那条记录。
- 修已定规则的 bug：先写能重现它的测试，确认它失败，再修。
- 要改已定的规则：先用白话问用户一次，记下用户的原话。
- 整块功能不要了：规则和测试一起删。

## 清单：写不成测试的坑

`.testcraft/checklist/<编号>.md`（清单目录下一层的每个 `.md` 都是一条）记写不成测试、又能从改动看出来的坑（老数据缺新字段还能不能读、改了接口要同步改哪几处、上线配置要跟着改），一条一个文件。改动命中某条的触发条件时，按它的"怎么查"查一遍，在改动记录的"## 清单"写一行。`testcraft checklist` 列出这次命中的条目。

- **什么时候加一条**：修 bug、出事故后，这个坑能写成测试的写测试，不进清单；写不成测试（跨模块的约定、老数据兼容、部署和配置），又能从改动的文件或增删的行看出来的，加一条。
- **怎么写**：

  ```markdown
  # 会话记录加字段时，老记录也要读得出来

  ## 触发

  - `src/session/**` 改到 `interface \w+Message`
  - `src/storage/schema.ts`

  ## 怎么查

  新字段在读老记录时有默认值；拿一份改动前的会话记录恢复一次，能打开。

  ## 来由

  fix/resume-crash：加了字段后，恢复老会话直接崩溃。
  ```

  触发每行一条：行首反引号写路径规则（几个用、隔开），后面可以加"改到"和反引号括起的文字（正则），这些文件增删的行里有这段文字才算。触发写得窄一点，命中了就该真去查；什么都触发的条目没人会认真查。
- 按分叉点那一版的清单查：这次新加的条目合并后才生效，这次删了、改了的照旧按原来的查。
- 删条目、放宽条目（去掉或改了触发条件、改了怎么查）算放水：写理由和"给用户过目"那一行，合并前给用户过目。条目不再有用（坑已经被测试守住、代码没了）才删。
- 查出问题的先停下来告诉用户，不要为了让清单过而改条目。

## 大改

新旧两套代码先并行，确认结果一样再换掉旧的。不删测试、不做假实现来让测试变绿。

- **用差分测试确认结果一样**：同样的输入同时喂给旧代码和新代码，结果要一样。旧代码原样留一份（旧函数或旧文件）让测试调得到。输入用性质测试的库随机生成，或者取一批真实数据的样本；真实数据先脱敏，不放进版本库。和结果无关的差别（空格、字段顺序、时间戳）先统一掉再比；新代码有意改了的地方，在测试里逐条列出来，不要放宽整个比较。
- **换掉旧代码时**：先确认每条规则都有普通的测试（例子或性质）守着，再删旧代码和差分测试。
  - 差分测试在同一分支里加了又删，放水检查看不到：在改动记录的"证明方式"写一行，例如"新旧结果一样 —— 跑命令：差分测试 500 组输入一致，旧代码已删，规则由 `tests/…` 守着"。
  - 差分测试已经合进默认分支，删它要写理由，合并前给用户过目，"给用户过目"那一行用白话写成"原来…，现在…，因为…"（例如"原来新旧两套价格算法并行比对，现在旧算法删了，因为新算法上线一个月结果都一样，各条价格规则另有测试守着"）。

## 测试时好时坏

同一份代码，一个测试这次没过、再跑又过了（整组里没过、单独跑能过，也算），就是时好时坏。testpace 在测试结果里点名、记进名单的（`testpace status` 列出名单和日志；项目的 `files` 经 `testpace run` 跑才有名单），就是这种。它说明测试或代码里有个条件没管住。靠重跑过关，以后它再红大家都当它又抽风了，真坏的时候也没人信它。

- **不靠重跑过关**：当一个要修的问题。测试或它测的代码这次改过的，当场照下面找原因（原因在业务代码里的照样先停下来）；和手上的活无关的，告诉用户是哪个测试、哪次跑没过、日志在哪（`testpace status` 的名单里有），问要不要现在修。
- **这些不算修，不要做**：加固定等待（`sleep`、`setTimeout`、`waitForTimeout`、等几秒再继续）；加重试或调大重试次数（测试里自己写的循环重试，测试文件里设的重试如 `test.describe.configure({ retries })`、`jest.retryTimes()`，配置里的 `retries`）；放大超时；跳过，或标成"已知不稳定"；把断言放宽到几种结果都算对。它们只是把问题藏起来。等一个具体的条件（元素出现、请求返回、数据写进库，`expect.poll`、`toPass`、`waitFor` 这类按条件轮询）是对的写法；只把这个等待的超时调大，不算修。
- **先找原因**，常见的几种：
  - 测试之间共用数据：两个测试改同一条记录、同一个账号，一起跑时互相踩。每个测试自己建数据，名字带唯一后缀。
  - 时间、随机数没固定：跨零点、跨月、时区、按当前时间算的到期；随机生成的输入。被测代码能从参数拿到当前时间、随机种子的，测试传固定值；页面测试里浏览器端的时间可以用替身固定（"放在哪一层测"）；测试不依赖那个时间、随机值就能修的（比如比较前先排序、名字加唯一后缀），在测试里修；非依赖不可、后端代码又只能自己读系统时间、自己生成随机数的，是业务代码的写法让它测不稳，先告诉用户。
  - 没等到真正准备好：页面还在加载、请求还没回来、后台任务还没跑完就去检查。等那个具体的条件，不等固定时长。
  - 依赖先后顺序：单独跑能过、跟着别的测试跑才没过（或者反过来），说明前一个测试留下了东西，或者这个测试靠前一个准备的东西。
  - 依赖外部服务：网络、第三方接口。照"放在哪一层测"，外部第三方服务用替身。
  - 业务代码在并发下本身有问题：几个请求同时到、几套环境一起跑时才出错。
- **先让它稳定地没过**：照怀疑的原因造出条件（把时间固定到跨零点、把两个测试放一起跑、换个顺序、同时发几个请求），让它每次都没过，才算找到了原因（`testpace files --repeat N <文件:行号>` 连跑 N 次、没过就停，可以拿来造失败；共用数据、先后顺序这类单独跑能过的，把造出失败时一起跑的几个文件都给它）；改完在同样的条件下跑通。造不出来，说明还没找到原因，不要凭猜测改。
- **原因在业务代码里**：这是测试抓到的真问题，先停下来用白话告诉用户，不要自己改业务代码，也不要改测试去迁就它。
- **实在找不到原因**：删掉，比留一个时好时坏的测试好；不要改成跳过。怀疑是业务代码在并发下的问题、又造不出来的，先告诉用户，不要删。删之前看这条规则还有没有别的测试守着，没有的告诉用户这条规则暂时没人守。已经合进默认分支的测试，删了要在放水理由里写"原来…，现在…，因为…"，合并前给用户过目；这次分支里新写的，放水检查和分叉点比、看不到，在改动记录的"证明方式"写一行删了哪个、为什么，完成时告诉用户。删了的测试不会经连跑去掉名单：在认出它的工作区里把它原来的文件整个跑一次（`testpace files <文件>`），全部通过，testpace 就把它从名单上去掉。
- **修好的**：用 `testpace files --repeat 10` 在造出失败的同样条件下连跑 10 次（单独跑就会失败的给 `<文件:行号>`；一起跑才失败的，给一起跑的那几个文件），跑的过程中不改代码。输出里说了把它从时好时坏名单上去掉才算修好；只说"都通过"、没说去掉的（比如有一次是框架重试后才过），用 `testpace status` 看它还在不在名单上，在的就还没修好。在改动记录的"证明方式"写一行：原因是什么、怎么造出它没过、改了什么、连跑 10 次都过。

## 改动记录

每次改动一个文件：`.testcraft/changes/<分支名>.md`（分支名里的 `/` 换成 `-`）。程序只认这次改动新加的文件，以前改动的记录不算数。

```markdown
# <分支名>

## 证明方式

- 余额不够时不能下单 —— 新测试 `tests/order.test.ts` 的"余额不够时不能下单"
- 订单列表按时间倒序 —— 已有检查（`tests/order-list.test.ts` 本来就守着）
- 导出按钮的位置 —— 需要用户看

## 放水理由

- `tests/price.test.ts`：规则变了，用户确认"会员价不再叠加优惠券"
- `tests/legacy/**`：旧版结算整块去掉了

## 守的代码

- `tests/total.test.ts` → `src/price.ts#total`

## 清单

- `resume-old-fields`：新字段读老记录时给了默认值，拿改动前的会话记录恢复过，能打开
```

- **证明方式**：每条动到的规则写一种：新测试 / 已有检查 / 跑命令 / 看代码 / 需要用户看。给人和检查员看。
- **放水理由**：`testcraft weaken` 标出来的每一处写一行，行首反引号里写文件（几个用、隔开；可以用路径规则，但要从具体目录写起，比如 `tests/price/**`；删测试、改测试约定、清单只认写明的路径或以 / 结尾的目录），冒号后面写为什么。只认行首的文件，理由里再用反引号写的是正文，不算文件。理由是写给检查员的，可以写技术细节。
- **给用户过目**：删测试、让测试不跑、程序的做法变了、删了或放宽了清单条目，合并前用户要在弹窗里看，而用户没有技术背景，看不懂放水理由。所以这几种每个文件再写一行，行首写文件（写法同放水理由，删测试、清单只认写明的路径或以 / 结尾的目录），冒号后面用白话写三件事：原来这些测试守的是什么，现在守的是什么，为什么改。业务规则变了的，引用用户确认的原话。不写函数名、代码、实现细节；不把放松说轻：删了就说删了、不查了就说不查了，不说成"挪了""调整"。例如：
  ```markdown
  ## 给用户过目

  - `tests/price.test.ts`：原来查满 100 减 20、不满 100 不减；现在满减改成减一半，不满 100 不减照旧查；你说新活动按减一半算
  ```
  弹窗里一个文件一项：程序列出看到的改动（删了哪几个测试、哪几个改了名也改了内容、加了跳过、旧版测试跑不过），后面就是你写的这一行。
- **清单**：`testcraft checklist` 列出的每条命中的条目写一行，行首反引号写编号，后面写怎么查的、结论。没写的，合并前 `testcraft check` 不过。
- **守的代码**：给已有代码补测试（这次没有对应的代码改动）时写，行首写 `测试` → `代码位置`（或只写代码位置），`#` 后面是函数名（或 const 声明的名字），不写就是整个文件。`testcraft prove` 在这里做改坏证明。

## 写完

1. `testpace focused`（或 `testpace files`）确认测试通过。
2. `testcraft prove`：新增的测试，证明能抓错。没过的按提示改测试，不要改业务代码去迁就测试；测试发现了业务代码里别的问题（不是用户这次让修的那个 bug），先停下来告诉用户。
3. `testcraft weaken`：没写理由的补上理由，要给用户过目的补上"给用户过目"那一行，或者把不该改的改回去。删测试用例也要写理由（改名、挪到别的文件不算删；改名时只删了整条语句的算删，要理由，`testcraft prove` 不要求它证明；改名时加了内容或改了原有语句的，照旧当新测试证明）。只改了已有测试的断言（换写法、改松），也要写理由，同一类改动可以用一条路径规则写一行。
4. `testcraft checklist`：命中的条目按"怎么查"查一遍，写进改动记录的"## 清单"。没改到规则的小改动也会命中，照样要查。
5. 用 `gatelight:review-tests` 请检查员复查：复查前跑 `testcraft review start`；复查中改测试，不重跑第 2、3 步（每改一次都要整份重来，中间跑的下一轮一改就作废）；问题都改完后跑 `testcraft review done`，再把这两步各跑一次。
6. 合并前 `testcraft check`（`testpace full` 里测试之前的一段）会要求用户过目其中业务上的几处：删测试、让测试不跑、程序的做法变了、删了或放宽了清单条目。它输出编号和要给用户看的文字：先在对话里用白话向用户说明每一处原来是什么样、现在改成什么样、为什么，再调用 gatelight 的 `confirm_with_user` 工具，repo、id、text 照输出原样填，text 一字不改（会弹窗，用户同意才算）。用户不同意的，改回去或换个做法。同意按文件记：同意过的文件没再动、给用户看的说明也没变，别处怎么改都不用再问；那个文件又改了，或说明改了，重跑 `testcraft check`，按新的编号再过目一次。别的（换断言写法、测试跟着代码改了接法、改测试配置和数据、依赖、约定）是技术调整，理由照样要写，不给用户过目，检查员复查时会看。
7. 完成时用白话告诉用户：这次动了哪些规则、每条凭什么证明、哪几处要用户亲自看、哪些规则还是暂定。
