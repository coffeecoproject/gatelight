# 按模块写代码

modwall 的约定：默认模块化，越界由程序拦。模块边界以 `.modwall/config.json` 为准（LayerMap 报的模块依赖和循环按它自己推断的划分，不作数）。

## 放在哪

- **新功能建新模块**：在模块根目录（配置的 `roots`）下新建一个目录，它就是一个模块，不用登记、不用问人。模块里再分子目录随意，它们不是子模块。
- 每个模块可以写一个 `MODULE.md`：一句职责、一句不做什么，会话开始时会给 agent 看。不写业务规则。
- **共享层**（`shared`）只放没有业务含义的东西：错误和结果、数据库连接、路由执行、身份校验这类，换个项目也能用。只有一个模块用的放回那个模块；拿不准归哪里的新代码，先归模块，不归共享层。共享层不能引用任何模块和装配层。
- **共享层不放模块之间的业务契约**：
  - 模块之间的业务类型和常量（状态、付款计划这类）归定义它的模块，从入口导出，别的模块经入口引用。
  - 由装配层接线的接口（一个模块要用、另一个模块提供的函数），由使用它的模块声明类型、从自己的入口导出，装配层把提供方的实现接进来。不在共享层集中放这类接口：集中放了，谁依赖谁就看不出来，成环也查不出来。
  - 例外：应用之间的接口契约副本（比如从后端接口生成给前端用的类型）放在各应用的共享层，按生成工具的要求放在一起。
- **装配层**（`app`）把各模块接起来：程序入口、路由注册、依赖组装。它可以引用各模块的入口和共享层，别人不能引用它。
- 代码文件要放在模块、共享层或装配层里。直接放在模块根目录下的文件没有归属，会被拦；唯一的例外是配置的 `app` 里点名写了它（写到这个文件、不用通配），它就归装配层，比如 Python 包的 `__init__.py`。归了装配层，模块就不能引用它：Python 里从别的模块拿东西写成 `from <根目录的包>.模块名 import …` 或 `from ..模块名 import …`，不写 `from <根目录的包> import 模块名`、`from .. import 模块名`（这两种会被记成引用了根目录的 `__init__.py`）。框架要求放在固定目录的文件（小程序页面、按文件路由的页面）由配置的 `map` 归到某个模块。
- 写文件的那一刻就会查引用：TypeScript、JavaScript 文件里用相对路径直接引用别的模块的内部文件（比如 `../booking/internal/slot`），这次写入会被拒绝。改成从对方的入口引用（`../booking` 或 `../booking/index.js`）；入口里没有要用的东西，先去对方入口新增导出（作为单独的一小步），再回来引用。别的语言、用别名写的引用写文件时不查，`modwall check` 照样查得出来。
- 项目代码不放进 LayerMap 不读的目录：目录名是 `node_modules`、`vendor`、`.venv`、`__pycache__`、`site-packages`、`.claude`、`.codex`、`.cursor`、`.pi` 的（不分大小写）。modwall 查不到里面的代码引用了谁，这类目录下的代码文件只有写进 `outside` 才算有归属。在模块、共享层、装配层里出现的会被拦，换个目录名搬出来（业务上叫 vendor 的模块也要换名字）；提交进仓库的第三方代码写进 `outside` 要用户同意。被 git 忽略的（装依赖生成的 `node_modules`）不受影响。

## 一个仓库里有几个应用时

配置写了 `apps`（比如前端和后端放在同一个仓库里）时，按应用分开：

- 每个应用各有一套模块：`apps` 里每个应用一组 `roots`、`shared`、`app`、`entry`、`map`，意思和上面一样，只管这个应用。新功能建在它所在应用的模块根目录下。注意 `apps` 是应用，`app` 是应用里的装配层。
- 模块名只要在一个应用里不重复。几个应用都有"课程"模块是正常的，它们是不同的模块，报告和会话开始的模块列表里写成 `应用名/模块名`，比如 `web/courses`、`server/courses`。
- **应用之间不能引用代码**，引用了按 R3 拦，不管引用的是对方的模块、共享层还是装配层。要共用的代码放进外面一层的 `shared`。应用之间通过接口（HTTP、生成的契约副本）打交道。
- 外面一层的 `shared` 是几个应用共用的代码，每个应用都能引用，它不能引用任何应用的代码。
- R1、R2、R4 每个应用自己算：只看同一个应用里的模块、入口和装配层。

## 用别的模块的东西

- 只从对方的**入口**引用（模块目录下第一层的 `index.ts`、`__init__.py` 这类，见配置的 `entry`）。
- 小程序里，模块对外的组件放在模块目录下第一层的 `components/`（`components/<组件>/`），别的模块只用这里的组件（`usingComponents`）；页面里的组件、模板（`<import>`、`<include>`）、样式（`@import`）不直接用别的模块的。这个组件该给别人用，就挪进 `components/`，作为单独的一小步；几个模块都用的通用组件、模板、样式放共享层。
- 样式、图片、JSON 这类文件也算：不直接 import 别的模块里的。图片、JSON 和代码一样从对方入口导出；样式不能经入口导出，几个模块都用的样式搬进共享层，只该对方用的，改成用对方入口导出的组件。
- 入口里没有要的东西：在对方入口**新增导出**，作为单独的一小步来做，说清楚为什么要导出。不要为了省事把对方内部的东西全从入口导出：`modwall check` 会列出这次给哪些入口新增了导出。
- **不给别的模块的已有函数加分支**：为新功能在对方新增一个函数。改了别人已有的导出函数、同时又在自己模块里新加了对它的调用，`modwall check` 会提示（R4）；正常的重构（改签名、同步更新调用处）不用管。
- **不在别的模块里写上自己的名字**：别的模块的名单、类型、枚举、常量、映射表、`switch`、数据库约束里，不为新功能加上它的名字、它的页面、它的来源。加了，对方就认识了用它的模块，以后每多一个用的地方都要回去改它，看引用还查不出来。改成对方收一个值（比如来源的文字由调用方给），或者由装配层把链接、实现接进来。旧代码里已经有这种写法的，不照着再加一项：顺手改成干净的写法，改动大的先告诉用户。这次新建了模块、又改了已有模块里已有的东西（声明，或它的新迁移里改、删已有的对象），`modwall check` 会提示（R4）；正常的重构不用管。
- 模块之间**不能成环**（数据库里经入口 schema 的引用也算进去）：A 用 B、B 又用 A 时，把真正通用、没有业务含义的东西下沉到共享层，或者通过参数传进来；两个模块确实分不开，就合成一个。不要为了躲开成环把业务类型、常量挪进共享层：成环说明模块要重新划分，拿不准就停下来问用户。
- 正式代码不引用 `outside` 里的文件（构建配置、脚本、迁移）和测试文件。

## 数据库（配置里写了 `database` 时）

数据库也按模块分，位置就是归属，不另外登记：

- **一个模块两个 schema**，名字由模块目录名转成小写加下划线（`adminAccess` → `admin_access`）：
  - 内部 schema（`admin_access`）：模块自己的表、序列、函数、视图；
  - 入口 schema（`admin_access_api`）：只放给别的模块用的视图、函数和类型（比如状态的枚举），**不放表**。它是数据库里的入口文件。
- 新功能要新表：建在自己模块的内部 schema 里，迁移放在自己模块目录下的迁移子目录（配置的 `database.migrations`）。共享层的迁移放在 `database.shared`。
- 迁移文件名以 14 位的时间戳开头（`20261118093000_create_orders.sql`），精确到秒，不能和别的迁移（包括别的模块的）重复。迁移只写正向，一个时间戳一个文件，不写回滚迁移（`.down.sql` 这类）。迁移由跑迁移的工具放进本模块的 `SECURITY DEFINER` 函数里整段执行：里面不写 `COMMIT`、`COPY … FROM STDIN`、`CONCURRENTLY`、`VACUUM`。
- **只引用别的模块入口 schema 里的对象**，不碰对方的内部 schema；入口里没有要的，在对方入口 schema 新增视图或函数，作为单独的一小步（那是对方的迁移）。要几个模块在一个事务里完成的事，由入口里的函数提供，或者装配层把同一个连接交给几个模块。
- **不在别的模块的入口上建视图**（`BEGIN ATOMIC` 写正文的函数也一样）：跨模块的读取写在函数正文（plpgsql，或 `AS $$…$$` 的 sql 函数）或应用代码里。视图叠在对方入口上，对方就删不掉、改不动自己的入口了。
- **入口只加不改**：改自己入口里的视图、函数时，新加一个，旧的等没有模块用了再删；类型只加不删（枚举只加值）。直接改旧的，用它的模块要到运行时才出错。别的模块的表列、函数签名可以用对方入口里的类型。
- **跨模块写入走对方入口里的函数**：不直接 `INSERT`、`UPDATE`、`DELETE` 对方入口里的视图；要写，就在对方入口加一个做这件事的函数（对方的迁移，单独一小步）。
- **只在自己的两个 schema 里建、改、删对象**：别的模块的、`shared` 里的对象由它们自己的迁移改；在别的模块的对象上挂触发器、规则、策略、索引，写注释、授权也算改它。迁移里不写 `CREATE SCHEMA`：模块的两个 schema 和 `shared` 由跑迁移的工具建。迁移和函数里不改 `search_path`（`SET`、`RESET search_path`、`set_config`）。
- **模块之间不建外键**：引用别的模块的数据只存它的 id，存在性和删除规则由应用经对方入口保证，删除一般改成软删除。指向 `shared` 的外键可以。
- 不写全名的就是本模块的对象：**函数一律带 `SET search_path = <本模块的内部 schema>, pg_temp`**（共享层的函数设成 `shared, pg_temp`），引用别的模块、`shared` 写带 schema 的全名。**函数一律 `SECURITY DEFINER`**（建函数时写上，`CREATE OR REPLACE` 不写会改回去）：以本模块的角色执行，入口函数才碰得到内部的表，函数里也切不了身份。要 `COMMIT` 的过程拆开或放到应用代码里。
- 检查按名字认 schema：表、列的别名、CTE 名、函数里的变量不和任何模块的 schema 同名；引用的表、视图名字和别的模块的 schema 同名时（比如读 `orders_api.orders`），起别名，用别名限定列。
- 给模块改名、拆模块不再只是搬目录：schema 名跟着目录名走，要写迁移改 schema 名、搬表，并改掉别的模块里写的全名。动手前先和用户商量。
- 共享层的 `shared` schema 只放没有业务含义的结构（比如迁移记录表），不引用模块；`public` 里不放对象（扩展自带的除外）。
- **每个模块一个同名的数据库角色**，程序每个事务开头由装配层或共享层的小函数切成要用库的模块的角色，所以模块的代码写自己的表不带 schema，引用别的模块写对方入口的全名；越界的读写数据库直接拒绝。迁移和模块的代码（包括模块里迁移目录以外的 `.sql`）里**不自己切身份**（`SET ROLE`、`RESET ROLE`、`SET SESSION AUTHORIZATION`、`set_config('role', …)`），要别的模块做事就走它的入口。注释、说明文字里写了这几个词也会被当成切身份，换个说法。
- 配置的 `database` 写了 `runtime`（比如 `"<module>_app"`）时，模块的代码切成的是本模块的**运行角色**（`orders_app`），不是模块的角色：运行角色只有本模块内部 schema 的使用权和表上的读写授权，不拥有对象、不建对象。新表在迁移里建（迁移仍以模块的角色跑），同一个迁移里给本模块的运行角色授读写（`GRANT SELECT, INSERT, UPDATE, DELETE`）；不给它 `CREATE`、不把表的主人改成它、不把它加成模块角色的继承成员，`modwall db check` 会报。入口的授权也要给别的模块的运行角色（模块的代码以运行角色读你的入口；函数、触发器以模块的角色执行，读别人入口的授给模块的角色）。
- 自己的入口视图、函数要授权给别的模块的角色用（入口 schema 的使用权、视图的读权限，项目一般有一个所有模块角色都是成员的组角色）；内部 schema 不授权给任何别的角色，自己的两个 schema 也不让别人建对象。

## 检查

- 改完代码用 Bash 跑 `modwall check`。它看整个项目，不分这次改的还是原来就有的，没有"老代码可以不管"。
- 越界按输出的"改法"改，改到清零。
- R1–R3、R5、R6 拦，R4 和入口新增导出只提示，"没检查到"是 LayerMap 没看全的地方，照列不拦。
- `modwall check` 静态读迁移文件；库里的现状由项目在整组里跑完迁移后用 `modwall db check --psql "<执行 SQL 的命令>"` 查。它报的越界改迁移或跑迁移的工具（角色、权限），不直接改库。
- **放宽规则**（往 `allow` 加例外，扩大 `shared`、`app`、`map`、`outside`，删掉或缩小 `roots`，往 `entry` 加文件名，删掉 `database` 或改它的目录、账号名，给 `database` 加上或改 `runtime`，删配置；有几个应用时还有：新加应用的 `shared`、`app`、`map`、`entry`，删掉或改名应用，单应用写法和按应用分组的写法之间切换）要用户同意：`modwall check` 会列出放宽项，先用白话向用户说明每一项放宽了什么、为什么不能按规则改，再调用 `confirm_with_user` 工具（会弹窗，用户同意才算；编号和文字照 `modwall check` 输出的填，一字不改）。同意按项记：同意过的那一项，配置别处再改也不用重新问。不要自己说"用户同意了"。能按改法改的，不申请例外。
- 结束前这个会话改过代码或配置、又没有通过记录时，会被拦一次，要求跑 `modwall check`。合并前 `modwall check` 是整组（`testpace full`）里最前面的一段，没通过就合不进默认分支。
- 用 Bash 改文件绕过了改文件前的路径检查，结束前和合并前照样会查出来。
