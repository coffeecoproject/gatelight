# 给项目接入 testpace

testpace 只靠仓库根目录的 `testpace.json` 认项目：有它，命令和 hook（合并门、停止门、测试节奏提醒）才对这个仓库起作用。接入要做的是写这个文件、配好三条命令，再加上下面几条默认的测试检查。

testpace 不管测试的写法风格（分几层、怎么组织、写多细），只默认确认测试真的在测东西。接入时不改测试本身。

接入的人常常看不懂测试的细节，所以由你按项目情况判断、直接做好，不要把"要不要加某条检查"这类技术选择抛给用户；做完用大白话告诉用户做了什么（见第 7 步）。

- **新项目**（新建的、提交很少的仓库）：建项目时一起接入，不另起一步。落地前跑全部检查和全部测试，这是约定，不用问用户。
- **老项目**：先改造成新项目的样子再接入：测试命令整理成三条、找测试的规则覆盖所有种类的测试、要数据库的测试改用独立的测试环境，在自己的分支上做。只动测试和脚本；要改业务代码时停下来告诉用户。只在这几种情况问用户：有测试找不到办法跑、全部测试跑一遍太久要取舍、要改业务代码。

## testpace.json

```json
{
  "fast": "pnpm -s check:fast",
  "files": "pnpm -s test:files",
  "full": "pnpm -s check:full",
  "tests": ["**/*.test.ts", "e2e/tests/**/*.spec.ts", "!**/fixtures/**"],
  "ignore": ["docs/**"]
}
```

| 字段 | 要做到什么 |
|---|---|
| `fast` | 快速检查，通常是类型检查加 lint，应当是增量的（几秒到十几秒）。`testpace focused` 每次先跑它 |
| `files` | 只跑给定的测试。testpace 把参数接在命令后面传进去，每个参数是一个测试文件（相对仓库根目录），或 `文件:行号`：只跑那一行声明的测试，用来重跑失败的那几个（测试框架的失败输出里通常就有这个位置）。参数写成 `文件:行号:列号` 的也要认：去掉列号，按 `文件:行号` 跑。各测试框架数列号的办法不一样（有的按转换后的代码数），列号原样交过去可能找不到测试。测试框架不能按行跑的，`文件:行号` 跑整个文件，多跑不出错。环境（数据库、服务）自己准备；有文件不存在、测试框架没加载到、文件里一个测试都没有，或按行跑时那一行没有测试，返回非零。测试都在、只是按条件全被跳过（比如只在 Linux 上跑）的不算失败，在输出里说一句 |
| `full` | 落地到默认分支前必须通过的、测试以外的检查：类型检查、lint、构建这些。不在这里跑测试。里面有构建步骤的（比如先打包页面、编译后台），构建产物（`dist/`、`build/` 等）要在 `.gitignore` 里：`testpace full` 跑完会核对工作区有没有变，产物没被忽略就算跑的过程中代码改过，通过也不记录。不要用 `ignore` 字段处理产物 |
| `tests` | 找测试文件的路径规则，以 `!` 开头的是排除。`testpace full` 在 `full` 通过后，把规则在工作区里找到的全部测试文件（已跟踪的和没被 .gitignore 忽略的新文件）一次交给 `files` 跑。新加的测试不用改配置就会被跑到。规则要覆盖项目里每一种测试，又只圈真正的测试文件：和测试放在同一目录下的练习脚本、工具脚本不能被圈进去（比如 `e2e/` 下既有测试又有导入练习时，写 `e2e/tests/**/*.spec.ts`，不写 `e2e/**/*.spec.ts`）。一个都找不到时整组不跑。合并门只认 `testpace full` 跑出的通过记录。把整套系统起起来跑的测试（页面测试、端到端验收）也要在规则里，不能排除掉、只留到发布后在服务器上跑；它们要的系统由 `files` 起好。页面测试测什么、放在哪一层，归写测试的约定管，这里只管它要在整组里 |
| `ignore` | 可选。不影响测试的路径，改了它们不用重跑。`**` 跨目录，`*` 不跨目录，结尾 `/` 表示整个目录。不要写 `**/*.md` 这类通配。`testpace.json` 自己不算忽略路径：改了它（包括改 `ignore`）要在改完的代码上重跑整组 |

三条命令都从仓库根目录运行、不需要交互、退出码 0 表示通过。不能有别的字段。

`files` 在整组时一次拿到全部测试文件，单元测试、数据库测试、页面测试混在一起，所以它要扛得住：
- 按路径把文件分给各自的运行器和配置（比如单元测试交给 Vitest，页面测试交给 Playwright），各自用自己的并发；并行、分片这类提速也做在这里。
- 要起环境的那部分（数据库、整套系统）每次调用只起一次，这一批文件都跑在它上面，跑完再收掉；不要每个文件起一次。
- 某一类一个文件都没拿到时，不起它的环境。

`full` 和 `files` 要用到的外部服务（比如起数据库、起整套系统的后台程序），在命令的最开始检查：缺了马上失败，说清楚缺什么、怎么补，不要跑到一半才报。`testpace full` 先跑 `full`，所以整组里测试要用的服务也放在 `full` 开头一起查，缺了不用等前面的测试跑完才知道。

合并门判断落到默认分支的代码时，读的是提交里的 `testpace.json`，不是工作区里的文件。删掉 `testpace.json` 的提交拿不到通过记录，agent 落不了地：项目要退出接入时，告诉用户由他自己在终端里提交。

## 默认的测试检查

这几条不是写法偏好，是"测试至少得真的在测东西"：没有它们，测试看着全过，其实什么都没测（假绿），合并门认的整组记录也就不可信。

| 检查 | 做法 |
|---|---|
| 测试里不能留着只跑这一个（`.only`） | 留着时只跑了那几个也报全过。优先用测试框架自带的开关（见下面各框架的做法）；没有开关的，用 lint 规则（如 eslint 的 jest、vitest 插件里的 `no-focused-tests`，Biome 的 `noFocusedTests`） |
| 每个测试都要有断言 | 只调用一下函数、什么都不判断的测试永远会过。优先在测试跑的时候查：测试框架自带的开关，或者数测试实际做了几次断言，写在辅助函数里的断言也认得出。做不到的，用 lint 规则（如 eslint 的 jest、vitest、playwright 插件里的 `expect-expect`） |
| `files` 给了不存在的文件要失败 | 见第 2 步。这条是 testpace 约定本身要求的，所有项目都要做到 |

各框架的做法（除了 node:test 的断言，都不用新装依赖）：

- **Vitest**：配置的 `test` 里写 `allowOnly: false` 和 `expect: { requireAssertions: true }`。
- **Playwright**：配置里写 `forbidOnly: true`。断言没有自带开关，加一个自定义报告器：`onTestEnd` 里只看通过的测试，在它的步骤（`result.steps`，逐层往下找）里找 `category` 是 `expect` 的，一个都没有就记下；`onEnd` 把记下的列出来，返回 `{ status: 'failed' }`，整轮就失败。往下找时跳过 `category` 是 `fixture`、`hook` 的步骤：共用的 fixture、`beforeEach` 里的断言不是测试自己的，算上它们，每个测试都会过关。只查 `tests` 规则圈的测试文件，准备登录状态这类 setup 不查。报告器写进配置的 `reporter`：命令行传 `--reporter` 会把配置里的整个换掉，`files` 要别的报告（比如给脚本读的 JSON）也写进配置。写好后放一个没有断言的测试跑一次，确认它被点名、整轮失败，再删掉。
- **node:test**：不加 `--test-only` 时 `.only` 不起作用，测试命令里别加它（`testpace run node-test` 不加），这条就不用做。断言没有自带开关，用 eslint 的 jest 插件的 `jest/expect-expect`，配上 `additionalTestBlockFunctions: ['test']`（插件认不出从 `node:test` 导入的 `test`）和 `assertFunctionNames: ['assert', 'assert.*', 't.assert.*']`。项目没有 eslint 时要新装依赖，照下面先问用户。
- **别的框架**：先找自带的开关，没有再用 lint 规则。

- **什么时候加**：新项目，或者项目还没有自己的 lint 和测试规范时，加上前两条。项目已经有自己的 lint 和测试规范的，不动它原有的 lint 配置；前两条还缺、又能用测试框架自带的开关或报告器补上（不用新装依赖）的，照样补上。所有项目都做 `files` 那条和第 6 步的抽查。
- **放在哪**：前两条要放进 `fast`、`files` 或 `full` 会跑到的地方（比如 lint 本来就在 `fast` 里），否则不起作用。
- **要新装依赖时**（比如项目完全没有 lint 工具），先用大白话问用户，比如"要给项目装一个检查工具，用来发现写坏的测试，会往项目里加一个依赖，可以吗"。用户不同意就跳过前两条，第 7 步告诉用户少了什么。
- **加上后先跑一次**：用 lint 规则查断言时，测试通过自己写的辅助函数断言的（比如 `expectSaved(page)`），把这些函数名配进规则（`expect-expect` 的 `assertFunctionNames`），别把它们误报成没有断言。剩下被报出来的已有测试多半是假绿：不改测试，把它们列给用户，用大白话说明，问用户怎么处理。
- `.skip`（暂时跳过某个测试）不禁止：有时是正当的。

## 步骤

1. **找项目已有的命令和测试**：看 `package.json` 的 scripts、Makefile、CI 配置、README、测试框架的配置。三条命令尽量直接用现成的，不另造一套；不是 JavaScript 项目（Go、Python、Swift 等）也一样写三条命令。`full` 放测试以外的全部检查；`tests` 照测试框架实际认的文件写（比如 Vitest 的 include、exclude），项目里有几种测试（单元、数据库、页面、端到端）就要都覆盖到。说不清某种测试怎么跑、或全部测试跑一遍太久要怎么取舍时，用大白话说明情况，请用户定；把整套系统起起来跑的测试排除出整组，不在可取舍的办法里。
2. **测试用 `node:test` 或 Vitest 的，`files` 一律用 `testpace run node-test` 或 `testpace run vitest`**，不自己写包装、不自己数测试，接入前项目里已有的这类包装和计数报告器删掉：它检查文件都在、每个文件都跑到了测试（Vitest 被项目配置排除、悄悄没跑的文件也查得出来），全被跳过时说一句；Vitest 按行跑，node:test 不能按行跑，按行给的整个文件跑。要先起环境、编译、按路径分给不同跑法的，脚本照旧做这些，到"用框架跑这几个文件"那一步调它（`--cwd` 换目录：node 的工作目录，或装着 Vitest、放着它配置的那个目录；`--node-arg`、`--vitest-arg` 原样交参数给框架，比如 `--node-arg=--import=tsx`、`--vitest-arg=--maxWorkers=2`），自己不再数测试。testpace 跑项目命令时 PATH 上一定有它自己。
   **testpace 还没内置的测试框架**（目前是 node:test、Vitest 以外的），写一个小脚本包一层（比如 `scripts/testpace.sh files a.test.ts b.test.ts:42`），把参数交给测试框架。测试框架能按行跑的（比如 Playwright、Vitest），按 `文件:行号` 交给它，带列号的先去掉列号；不能的，去掉行号和列号跑整个文件，在输出里说一句。很多测试框架把参数当成筛选条件：给了几个文件、其中一个不存在时，只跑找得到的那些，照样报通过。所以脚本要自己检查每个文件都存在、测试框架加载了它、里面有测试，否则返回非零。按条件跳过的测试（比如只在某个系统上跑）算有测试：整组里它们同样被跳过，`files` 不比整组更严；一个文件的测试全被跳过时，在输出里说一句，让人知道它这次什么都没验证。
3. **写 `testpace.json`**，放在仓库根目录，进版本库。然后跑 `testpace status` 看合并门那一行：
   - 说合并门没配：会话开始时 testpace 会自动配上；用户自己删掉过的，问用户要不要跑 `testpace install` 配回去。
   - 说 git 太旧：告诉用户升级 git（要 2.54 以上），不要自己装。在那之前合并门不起作用，其余照常。
4. **加默认的测试检查**（见上一节）。
5. **改项目说明**：项目给 agent 的说明（CLAUDE.md、AGENTS.md 等）里写着直接跑测试命令的地方，改成 testpace 的命令。直接跑项目自己的命令不留记录，合并门不认。说明里要求直接在默认分支上改、改完就提交的，问用户要不要改成下面的节奏（在分支上开发、成批合并）。
6. **检查**：
   - `testpace verify <测试文件>...`：它还核对给的每个文件都在 `tests` 规则里（不在就是整组跑不到这一类测试）。项目里的测试交给不同工具或配置跑的（比如前端用 Vitest、接口用 node:test、另有一套数据库测试），每种各挑一个跑得快的文件一起给它；依赖外部服务的那种，服务起得来时也给上。最后一行应当是"查了的都通过"。它由程序实际去跑，核对配置没写坏、三条命令找得到、合并门在把关、`files` 给了不存在的文件要失败，每个文件能通过、混进不存在的路径要失败、`文件:行号` 和 `文件:行号:列号` 能用，几个文件一起交给 `files` 能通过。有"没通过"的，照输出和日志改好再核对，不要只凭自己看过就算数。测试框架能按行跑的，再看一眼 `testpace files <文件:行号>` 的输出里只跑了那一个测试。
   - **抽查测试能不能抓到错**：挑一两个和主要功能相关的测试，把它测的那处代码故意改坏（比如把 `>=` 改成 `>`，或删掉一行调用），用 `testpace files` 跑这个测试，它应当失败。改之前先记下原来的内容，看完马上改回去，再确认代码和改之前一模一样（文件已进版本库且原本没有未提交改动时用 `git diff`，否则逐字对比记下的原文）。优先挑没有未提交改动的文件，免得和用户的改动搅在一起。改坏了测试还通过，说明这个测试没真正测到那处代码：不要自己改测试，第 7 步告诉用户。
   - 所有改动都做完后，跑一次 `testpace full`（能放后台就放后台，结束后用 `testpace status` 看结果），确认整组能通过，顺便知道它要跑多久。
7. **用大白话告诉用户**，不用术语，比如：
   > 这个项目接好了测试管理：以后改完代码会先跑相关的测试，合并到主分支前会确认全部测试都通过。另外加了两条检查，防止测试看着通过、其实什么都没测。抽查了 2 个测试，故意改坏代码后它们都能发现。全部测试跑一遍要 3 分钟。

   有跳过的检查、抽查没抓到错的测试，也在这里说清楚。
8. **提交前先问用户**。接入后，落到默认分支的提交都要有那份代码的整组通过记录。记录按跑的那一刻工作区的内容算：第 6 步的整组跑完后又改了文件（`ignore` 里的除外），要再跑一次，合并门才会放行。

## 接入以后的节奏

- 升级 testpace 后（约定可能加了新要求），在已接入的项目里跑一次 `testpace verify <测试文件>...`（每种测试各一个），有没通过的就改项目的命令。

- 每个任务在自己的分支上做，最好是自己的 worktree。
- 改完跑 `testpace focused`：`fast` 加上和改动相关的测试。在分支上不跑整组；在默认分支上直接改的，它提示跑整组时照做。
- 有失败，用 `testpace files <文件:行号>` 只重跑失败的那几个测试。
- 整组在合回默认分支时跑：做完的几个分支一起合，跑一次 `testpace full`，通过了再落地（`testpace:merge` 技能）。
- 同一个工作区一次只跑一轮测试：已经有 testpace 的命令在跑时，再起一个会直接退出（退出码 3），等它结束再跑。

`focused` 靠 layermap 按改动选测试：PATH 里要有 `layermap` 命令（装上 layermap 插件并开新会话就有）。没有时 `focused` 只跑 `fast`，然后建议跑整组；其余命令和合并门照常。
