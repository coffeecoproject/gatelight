# 给项目接入 testpace

testpace 只靠仓库根目录的 `testpace.json` 认项目：有它，命令和 hook（合并门、停止门、测试节奏提醒）才对这个仓库起作用。接入要做的是写这个文件、配好三条命令，再加上下面几条默认的测试检查。

testpace 不管测试的写法风格（分几层、怎么组织、写多细），只默认确认测试真的在测东西。接入时不改测试本身。

接入的人常常看不懂测试的细节，所以由你按项目情况判断、直接做好，不要把"要不要加某条检查"这类技术选择抛给用户；做完用大白话告诉用户做了什么（见第 7 步）。

## testpace.json

```json
{
  "fast": "pnpm -s check:fast",
  "files": "pnpm -s test:files",
  "full": "pnpm -s test:full",
  "ignore": ["docs/**"]
}
```

| 字段 | 要做到什么 |
|---|---|
| `fast` | 快速检查，通常是类型检查加 lint，应当是增量的（几秒到十几秒）。`testpace focused` 每次先跑它 |
| `files` | 只跑给定的测试。testpace 把参数接在命令后面传进去，每个参数是一个测试文件（相对仓库根目录），或 `文件:行号`：只跑那一行声明的测试，用来重跑失败的那几个（测试框架的失败输出里通常就有这个位置；输出里写成 `文件:行号:列号` 的，也要认）。测试框架不能按行跑的，`文件:行号` 跑整个文件，多跑不出错。环境（数据库、服务）自己准备；有文件不存在、测试框架没加载到、文件里一个测试都没有，或按行跑时那一行没有测试，返回非零。测试都在、只是按条件全被跳过（比如只在 Linux 上跑）的不算失败，在输出里说一句 |
| `full` | 落地到默认分支前必须通过的全部检查和测试。合并门只认 `testpace full` 跑出的通过记录。里面有构建步骤的（比如先打包页面、编译后台再测），构建产物（`dist/`、`build/` 等）要在 `.gitignore` 里：`testpace full` 跑完会核对工作区有没有变，产物没被忽略就算跑的过程中代码改过，通过也不记录。不要用 `ignore` 字段处理产物 |
| `ignore` | 可选。不影响测试的路径，改了它们不用重跑。`**` 跨目录，`*` 不跨目录，结尾 `/` 表示整个目录。不要写 `**/*.md` 这类通配。`testpace.json` 自己不算忽略路径：改了它（包括改 `ignore`）要在改完的代码上重跑整组 |

三条命令都从仓库根目录运行、不需要交互、退出码 0 表示通过。不能有别的字段。

合并门判断落到默认分支的代码时，读的是提交里的 `testpace.json`，不是工作区里的文件。删掉 `testpace.json` 的提交拿不到通过记录，agent 落不了地：项目要退出接入时，告诉用户由他自己在终端里提交。

## 默认的测试检查

这几条不是写法偏好，是"测试至少得真的在测东西"：没有它们，测试看着全过，其实什么都没测（假绿），合并门认的整组记录也就不可信。

| 检查 | 做法 |
|---|---|
| 测试里不能留着只跑这一个（`.only`） | 留着时只跑了那几个也报全过。优先用测试框架自带的开关，比如 Playwright 的 `forbidOnly: true`；没有开关的，用项目已有的 lint 规则（如 eslint 的 jest、vitest 插件里的 `no-focused-tests`，Biome 的 `noFocusedTests`） |
| 每个测试都要有断言 | 只调用一下函数、什么都不判断的测试永远会过。用项目已有的 lint 规则（如 eslint 的 jest、vitest、playwright 插件里的 `expect-expect`）；测试框架自带"测试必须有断言"的开关时也可以用它 |
| `files` 给了不存在的文件要失败 | 见第 2 步。这条是 testpace 约定本身要求的，所有项目都要做到 |

- **什么时候加**：新项目，或者项目还没有自己的 lint 和测试规范时，加上前两条。项目已经有自己的 lint 和测试规范的，不动它原有的配置，只做 `files` 那条和第 6 步的抽查。
- **放在哪**：前两条要放进 `fast`、`files` 或 `full` 会跑到的地方（比如 lint 本来就在 `fast` 里），否则不起作用。
- **要新装依赖时**（比如项目完全没有 lint 工具），先用大白话问用户，比如"要给项目装一个检查工具，用来发现写坏的测试，会往项目里加一个依赖，可以吗"。用户不同意就跳过前两条，第 7 步告诉用户少了什么。
- **加上后先跑一次**：测试通过自己写的辅助函数断言时（比如 `expectSaved(page)`），把这些函数名配进规则（`expect-expect` 的 `assertFunctionNames`），别把它们误报成没有断言。剩下被报出来的已有测试多半是假绿：不改测试，把它们列给用户，用大白话说明，问用户怎么处理。
- `.skip`（暂时跳过某个测试）不禁止：有时是正当的。

## 步骤

1. **找项目已有的命令**：看 `package.json` 的 scripts、Makefile、CI 配置、README。三条命令尽量直接用现成的，不另造一套；不是 JavaScript 项目（Go、Python、Swift 等）也一样写三条命令。缺哪一条（比如没有类型检查可做 `fast`，或说不清落地前该跑哪些算 `full`），给出你建议的做法，用大白话说明它是干什么的，请用户确认，不要不问就定，也不要只丢给用户一个术语让他选。
2. **`files` 接不了文件路径或 `文件:行号` 时**，写一个小脚本包一层（比如 `scripts/testpace.sh files a.test.ts b.test.ts:42`），把参数交给测试框架。测试框架能按行跑的（比如 Playwright、Vitest），`文件:行号` 原样交给它；不能的，去掉行号（和列号）跑整个文件，在输出里说一句。很多测试框架把参数当成筛选条件：给了几个文件、其中一个不存在时，只跑找得到的那些，照样报通过。所以脚本要自己检查每个文件都存在、测试框架加载了它、里面有测试，否则返回非零。按条件跳过的测试（比如只在某个系统上跑）算有测试：整组里它们同样被跳过，`files` 不比整组更严；一个文件的测试全被跳过时，在输出里说一句，让人知道它这次什么都没验证。
3. **写 `testpace.json`**，放在仓库根目录，进版本库。然后跑 `testpace status` 看合并门那一行：
   - 说合并门还没配：问用户后跑 `testpace install`。它改的是用户的全局 git 配置，这台机器配一次，所有项目、所有工作区都生效，不往项目里写文件，也不影响项目自己的钩子。
   - 说 git 太旧：告诉用户升级 git（要 2.54 以上），不要自己装。在那之前合并门不起作用，其余照常。
4. **加默认的测试检查**（见上一节）。
5. **改项目说明**：项目给 agent 的说明（CLAUDE.md、AGENTS.md 等）里写着直接跑测试命令的地方，改成 testpace 的命令。直接跑项目自己的命令不留记录，合并门不认。说明里要求直接在默认分支上改、改完就提交的，问用户要不要改成下面的节奏（在分支上开发、成批合并）。
6. **检查**：
   - `testpace verify <测试文件>...`：项目里的测试交给不同工具或配置跑的（比如前端用 Vitest、接口用 node:test、另有一套数据库测试），每种各挑一个跑得快的文件一起给它；依赖外部服务的那种，服务起得来时也给上。最后一行应当是"查了的都通过"。它由程序实际去跑，核对配置没写坏、三条命令找得到、合并门在把关、`files` 给了不存在的文件要失败，每个文件能通过、混进不存在的路径要失败、`文件:行号` 和 `文件:行号:列号` 能用，几个文件一起交给 `files` 能通过。有"没通过"的，照输出和日志改好再核对，不要只凭自己看过就算数。测试框架能按行跑的，再看一眼 `testpace files <文件:行号>` 的输出里只跑了那一个测试。
   - **抽查测试能不能抓到错**：挑一两个和主要功能相关的测试，把它测的那处代码故意改坏（比如把 `>=` 改成 `>`，或删掉一行调用），用 `testpace files` 跑这个测试，它应当失败。改之前先记下原来的内容，看完马上改回去，再确认代码和改之前一模一样（文件已进版本库且原本没有未提交改动时用 `git diff`，否则逐字对比记下的原文）。优先挑没有未提交改动的文件，免得和用户的改动搅在一起。改坏了测试还通过，说明这个测试没真正测到那处代码：不要自己改测试，第 7 步告诉用户。
   - 所有改动都做完后，把 `testpace full` 放后台跑一次，确认整组能通过，顺便知道它要跑多久。
7. **用大白话告诉用户**，不用术语，比如：
   > 这个项目接好了测试管理：以后改完代码会先跑相关的测试，合并到主分支前会确认全部测试都通过。另外加了两条检查，防止测试看着通过、其实什么都没测。抽查了 2 个测试，故意改坏代码后它们都能发现。全部测试跑一遍要 3 分钟。

   有跳过的检查、抽查没抓到错的测试，也在这里说清楚。
8. **提交前先问用户**。接入后，落到默认分支的提交都要有那份代码的整组通过记录。记录按跑的那一刻工作区的内容算：第 6 步的整组跑完后又改了文件（`ignore` 里的除外），要再跑一次，合并门才会放行。

## 接入以后的节奏

- 升级 testpace 后（约定可能加了新要求），在已接入的项目里跑一次 `testpace verify <测试文件>...`（每种测试各一个），有没通过的就改项目的命令。

- 每个任务在自己的分支上做，最好是自己的 worktree。
- 改完跑 `testpace focused`：`fast` 加上和改动相关的测试。在分支上不跑整组；在默认分支上直接改的，它提示跑整组时照做。
- 有失败，用 `testpace files <文件:行号>` 只重跑失败的那几个测试。
- 整组在合回默认分支时跑：做完的几个分支一起合，跑一次 `testpace full`，通过了再落地（`testpace:merge` 技能）。
- 同一个工作区一次只跑一轮测试：已经有 testpace 的命令在跑时，再起一个会直接退出（退出码 3），等它结束再跑。

`focused` 靠 layermap 按改动选测试：PATH 里要有 `layermap` 命令（装上 layermap 插件并开新会话就有）。没有时 `focused` 只跑 `fast`，然后建议跑整组；其余命令和合并门照常。
