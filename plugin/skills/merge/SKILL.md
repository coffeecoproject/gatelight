# 合并一批分支

接入了 testpace 的仓库，开发在各自的分支上做，只跑相关测试；整组留到合回默认分支时跑。几个做完的分支一起合，只跑一次整组，比每个分支单独合、各跑一次省得多。

合并门照常把关：落到默认分支的那份代码必须有 `testpace full` 的通过记录。记录按代码内容算，所有 worktree 共用，所以在合并分支上测过、默认分支快进过去的，不用重跑。

下面的 `main` 指仓库的默认分支，以 `testpace status` 和 git 里实际的为准。

## 步骤

1. **定要合哪些分支**。用户点了名的就合那些；没点名的，列出还没合进去的分支（`git branch --no-merged main`）给用户挑，不要自己决定。每个分支都要已经提交干净：它所在的 worktree 没有未提交的改动，有就先问那个分支的主人（用户或对应的会话），不替它提交。
2. **找一个干净的地方合**。主目录在 `main` 上而且没有未提交改动，就在主目录里做；否则开一个新 worktree，按项目说明准备好环境（依赖、`.env`、服务）。不要在别的会话正在用的目录里做。
3. **建合并分支并合进来**：从最新的 `main` 建 `merge/<日期时间>`，把选中的分支一个个合进去（`git merge --no-ff --no-edit <分支>`）。
   - 有冲突时，机械性的（比如两边各加了一段、只是位置挨着）可以解决；涉及逻辑取舍的，停下来告诉用户是哪两个分支、哪些文件，问怎么办。不要用 `-X ours`、`-X theirs` 这类办法一刀切。
4. **跑整组**：在合并分支上跑 `testpace full`。它依次跑几段，一段没过就停：先是这个仓库接入了的检查（比如模块边界、测试写法），再是项目的 `full`，最后是全部测试。要跑几分钟：能把命令放到后台的就放后台，不要干等；结束后用 `testpace status` 看结果。
5. **通过了**：把这次合了哪些分支、整组用时告诉用户，**用户确认后**再落地：在 `main` 所在的目录里 `git merge --ff-only merge/<...>`。要推送的，推送也先问。
   - 快进不了，说明这期间 `main` 又有了新提交：把最新的 `main` 合进合并分支，再跑一次整组。
6. **失败了**：先看是哪一段没过，输出的第一行写着（"整组失败：某一段没通过"）。
   - **测试之前的检查没过**（不是测试失败）：那一段自己的输出说了哪里不对、怎么改，照它做。
     - 输出里让你调用 `confirm_with_user` 的：是要用户同意的改动。各分支上用户同意过的那几项不会再问，列出来的是还没同意的。照输出先用白话告诉用户每一项，再弹窗；用户同意后重跑整组，不同意的按下一条办。
     - 只是要在合并后的代码上重跑一遍的（输出里给了要跑的命令，比如重新证明新测试能抓错）：在合并分支上跑那条命令，再跑整组。
     - 要改代码、改配置、补记录的：对照各分支改了哪些文件，找出是哪个分支引起的，按下面"拿出来"办。单独都通过、合在一起才不过的（比如两个分支合起来才越界），告诉用户是哪两个分支。
   - **测试失败**：从失败的测试找是哪个分支引起的：看失败的测试测的是哪块代码，对照各分支改了哪些文件（`git diff --stat main...<分支>`）。拿不准时，在那个分支自己的 worktree 里用 `testpace files <文件:行号>` 跑失败的测试；单独跑都通过、合在一起才失败的，是分支之间互相影响，告诉用户。
   - 把引起失败的分支拿出来：合并分支回到 `main`（`git reset --hard main`，只对这个临时分支做），重新合其余的分支，再跑一次整组。
   - 告诉用户拿出了哪个分支、为什么，它回到自己的分支上修。不要在合并分支上直接改代码修测试。
   - 重跑没过的测试时它过了，testpace 会点名它时好时坏、记进名单。它不是这批分支引起的（各分支都没碰它测的代码）时，不拿出分支：告诉用户是哪个测试、两次的日志在哪，用户同意后再跑一次整组落地，它留在名单上另外修。不要不说就重跑整组过关。
7. **收尾**：列出已经合进去的分支和它们的 worktree，问用户要不要删。合并分支落地后可以删掉。

## 什么时候不攒

- 紧急修复，或者别的分支等着用的改动，可以单独合，只为它跑一次整组。
- 一批不要攒太多：整组失败时，分支越多越难判断是谁引起的。
