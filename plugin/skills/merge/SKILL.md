# 合并分支

接入了 testpace 的仓库，开发在各自的分支上做：每轮跑一次相关的已有测试、只看不追，不写新测试。把关集中在合回默认分支这一步：用户说合，才把这次的测试写上，再在合并后的代码上跑整组。这一步是兜底的，照下面的步骤严格做，不省。

一个分支合一次，不攒：需求定了就写测试、合进去。测试要趁做这个分支的会话还在、还知道这次定了哪些规则的时候写。

做完一个任务不要自己合：告诉用户做完了，等用户说合。

合并门照常把关：落到默认分支的那份代码必须有 `testpace full` 的通过记录。记录按代码内容算，所有 worktree 共用，所以在合并分支上测过、默认分支快进过去的，不用重跑。

下面的 `main` 指仓库的默认分支，以 `testpace status` 和 git 里实际的为准。

## 步骤

1. **定要合哪些分支**。默认是这个会话自己做的那个分支。
   - 用户点了别的分支的名的，一起合。别的分支的测试该由做它的会话写：你没看过那边的对话，不替它写。它改了业务代码却一个测试文件都没动的，落地后告诉用户一句是哪个分支。它所在的 worktree 有未提交改动的，是还在做的：不合，告诉用户，不替它提交。
   - 这个会话没有自己的分支（比如在主目录里被叫来合），用户又没点名：列出还没合进去的分支（`git branch --no-merged main`）给用户挑。
2. **把测试补齐**，然后 `testpace focused` 通过，把这个分支提交干净。
   - 开发中留着没过的旧测试（因为用户这次改了需求才不过的）：照定下来的规则改掉。
   - 仓库接入了 testcraft（有 `.testcraft/` 目录）的：照 gatelight:write-tests 技能"什么时候写"一节，把这次定下来的规则列出来，交给一个子代理写新测试，旧测试也交给它一起改。这次没改到规则的不用写。
3. **找一个干净的地方合**。主目录在 `main` 上而且没有未提交改动，就在主目录里做；否则开一个新 worktree，按项目说明准备好环境（依赖、`.env`、服务）。不要在别的会话正在用的目录里做。
4. **建合并分支并合进来**：从最新的 `main` 建 `merge/<日期时间>`，把要合的分支合进去（`git merge --no-ff --no-edit <分支>`；有几个就一个个合）。
   - 有冲突时，机械性的（比如两边各加了一段、只是位置挨着）可以解决；涉及逻辑取舍的，停下来告诉用户是哪些文件、和 `main` 上的哪次改动冲突，问怎么办。不要用 `-X ours`、`-X theirs` 这类办法一刀切。
5. **跑整组**：在合并分支上跑 `testpace full`。它依次跑几段，一段没过就停：先是这个仓库接入了的检查（比如模块边界、清单），再是项目的 `full`，最后是全部测试。要跑几分钟：能把命令放到后台的就放后台，不要干等；结束后用 `testpace status` 看结果。
6. **通过了**：落地是在 `main` 所在的目录里 `git merge --ff-only merge/<...>`。
   - 用户这次说了要合回 `main` 的：直接落地，不再问一次。落地后把合了哪些分支、整组用时、解过哪些冲突告诉用户。
   - 是你自己提出要合的，或者要落地的和用户说的不一样了（拿出过分支）：先把这些告诉用户，**用户确认后**再落地。
   - 要推送的，推送先问。
   - 快进不了，说明这期间 `main` 又有了新提交：把最新的 `main` 合进合并分支，再跑一次整组。
7. **失败了**：先看是哪一段没过，输出的第一行写着（"整组失败：某一段没通过"）。
   - **测试之前的检查没过**（不是测试失败）：那一段自己的输出说了哪里不对、怎么改，照它做。
     - 输出里让你调用 `confirm_with_user` 的：是要用户同意的改动。分支上用户同意过的那几项不会再问，列出来的是还没同意的。照输出先用白话告诉用户每一项，再弹窗；用户同意后重跑整组，不同意的回到分支上改掉。
     - 要改代码、改配置的：回到分支上改，再合一次。
   - **测试失败**：回到这个分支自己的 worktree 里，用 `testpace files <文件:行号>` 跑失败的测试，找到原因修好，提交后重新建合并分支再合。不要在合并分支上直接改代码修测试。
   - **一次合了几个分支的**：从失败的测试找是哪个分支引起的：看失败的测试测的是哪块代码，对照各分支改了哪些文件（`git diff --stat main...<分支>`）。把引起失败的分支拿出来：合并分支回到 `main`（`git reset --hard main`，只对这个临时分支做），重新合其余的分支，再跑一次整组；告诉用户拿出了哪个分支、为什么。单独都通过、合在一起才失败的，是分支之间互相影响，告诉用户是哪两个分支。
   - 重跑没过的测试时它过了，testpace 会点名它时好时坏、记进名单。它不是这次要合的分支引起的（分支没碰它测的代码）时：告诉用户是哪个测试、两次的日志在哪，用户同意后再跑一次整组落地，它留在名单上另外修。不要不说就重跑整组过关。
8. **收尾**：列出已经合进去的分支和它们的 worktree，问用户要不要删。合并分支落地后可以删掉。
